# WordPress Theme Boilerplate - Current Setup Analysis

## 1. BLOCK STRUCTURE (src/blocks/core/)

### Current Organization
- **Location**: `/src/blocks/core/`
- **22 Core Blocks** currently defined:
  - button, buttons, columns, cover, details, group, heading, image, list-item, list, media-text, navigation, navigation-link, navigation-submenu, paragraph, post-date, post-excerpt, post-template, post-title, pullquote, query, site-logo

### Individual Block Structure
Each block is **minimal** with only one TypeScript file per block:
```
src/blocks/core/[block-name]/
└── [block-name].ts
```

**Example - Button Block**:
```
src/blocks/core/button/
└── button.ts (287 bytes)
```

**Example - Heading Block**:
```
src/blocks/core/heading/
└── heading.ts (231 bytes)
```

### Block File Content Pattern
Each block `.ts` file follows this pattern:
```typescript
import type { ThemeJson } from '../../theme.d.js';

const config: Partial<ThemeJson> = {
    "settings": {
        "blocks": {
            "core/[block-name]": {}
        }
    },
    "styles": {
        "blocks": {
            "core/[block-name]": {}
        }
    }
};

export default config;
```

**Purpose**: These files define theme.json settings and styles for core WordPress blocks (theme-level customization only, NOT functional block code).

## 3. BLOCK REGISTRATION

### Registration Flow

#### A. Theme.json Generation (`bin/build-theme-json.js`)
1. **Loads theme base config** from `src/blocks/theme.ts`
2. **Scans `src/blocks/core/`** for block directories
3. **Loads each block's TypeScript config** (e.g., `button.ts`)
4. **Deep merges** all block configs into the theme base
5. **Generates `/theme.json`** with combined settings/styles
6. **Generates separate style JSON files** in `/styles/` directory (for block-specific styles)

#### B. PHP Block Registration (`functions.php`)
```php
use RalfHortt\WPBlock\BlockManifest;

// This line triggers WordPress block type registration
(new BlockManifest(__DIR__ . '/build/blocks/blocks-manifest.php'))->register();
```

#### C. BlockManifest Class (from `vendor/ralfhortt/wp-block/src/BlockManifest.php`)
- Uses WordPress function: `wp_register_block_types_from_metadata_collection()`
- Reads `blocks-manifest.php` (generated by wp-scripts)
- Registers all block types at the `init` hook

**Key Point**: Currently, **NO block.json files are created**. Block registration relies on the manifest system.

### Theme.json Structure
**Generated at**: `/theme.json`
- Contains merged settings and styles for all core blocks
- Includes theme-level customization
- Supports theme.json v3 schema

**Example from current theme.json**:
```json
{
  "$schema": "https://schemas.wp.org/trunk/theme.json",
  "version": 3,
  "settings": {
    "blocks": {
      "core/button": {},
      "core/buttons": {},
      "core/heading": {},
      ...
    }
  },
  "styles": {
    "blocks": {
      "core/button": {...},
      ...
    }
  }
}
```

## 4. SCSS/CSS HANDLING

### SCSS Source Structure
**Location**: `/src/css/`
```
src/css/
├── 1-tools/          (SCSS tools/functions - currently commented out)
├── 2-generic/        (Global resets, custom media queries)
├── 3-elements/       (HTML element styles)
├── 4-components/     (Reusable components)
├── 5-blocks/         (WordPress block styles)
├── 6-utilities/      (Utility classes)
├── app.scss          (Main entry point - compiled to build/assets/app.scss.css)
├── editor-styles.scss (Editor-specific styles - imports app.scss)
└── login.scss        (Login page styles)
```

### SCSS Organization Pattern (ITCSS: Inverted Triangle CSS)
1. **1-tools**: Mixins, functions (ITCSS Layer 1)
2. **2-generic**: Resets, normalize (ITCSS Layer 2)
3. **3-elements**: Default HTML elements (ITCSS Layer 3)
4. **4-components**: Component styles (ITCSS Layer 4)
5. **5-blocks**: WordPress block styles (ITCSS Layer 4)
6. **6-utilities**: Utility/helper classes (ITCSS Layer 5)

### Block-Specific SCSS
**Location**: `/src/css/5-blocks/`
```
5-blocks/
├── button.scss       (Currently styled: .wp-block-button)
└── README.md
```

Only button.scss is currently implemented. Blocks can be styled using standard WordPress class names:
- `.wp-block-[namespace]-[blockname]`
- Example: `.wp-block-button`, `.wp-block-paragraph`

### CSS Compilation
- **Input**: SCSS files (`src/css/*.scss`)
- **Processor**: PostCSS (configured in `postcss.config.js`)
- **Output**: CSS files in `/build/assets/`
  - `app.scss.css` (main stylesheet)
  - `app.scss-rtl.css` (RTL version)
  - `editor-styles.scss.css` (editor stylesheet)
- **Source Maps**: Generated (`.css.map` files)

### PostCSS Configuration
```javascript
module.exports = {
    plugins: {
        cssnano: { preset: "default" },
        "postcss-custom-media": {},
        "postcss-easing-gradients": {},
    },
};
```

**Plugins used**:
- **cssnano**: CSS minification/optimization
- **postcss-custom-media**: Custom media queries
- **postcss-easing-gradients**: Advanced gradient support

### SCSS Features Available
- **SCSS @use syntax**: Used in files (modern, modular approach)
- **CSS Custom Media**: Via PostCSS plugin
- **Easing Gradients**: Advanced gradient effects
- **RTL Support**: Automatically generated

## 5. BLOCK.JSON METADATA

### Current State
**NO block.json files are currently in the codebase** ✗

### Block Registration Without block.json
Current flow bypasses block.json entirely:
1. WordPress `create-block` CLI would generate `block.json` if used
2. Current system doesn't use standalone `block.json` files
3. Block metadata is only in `theme.ts` files (theme.json only)

### Where Block Metadata Would Go
If implemented, block.json files would be at:
```
src/blocks/custom/[namespace]/[block-name]/
├── block.json
├── index.ts
├── edit.tsx
├── save.tsx
├── render.php
├── style.scss
└── index.scss
```

### Block Manifest Generation
- **Created by**: wp-scripts build command with `--blocks-manifest` flag
- **Location**: `build/blocks/blocks-manifest.php`
- **Contains**: PHP array of all block metadata from discovered block.json files
- **Currently**: Likely empty or minimal since no block.json files exist

### TypeScript Definitions
**File**: `/src/blocks/theme.d.ts` (48.5 KB)
- Generated from: `bin/generate-theme-types.js`
- Provides full TypeScript support for theme.json structure
- Allows IDE autocomplete for all valid theme.json properties

## SUMMARY: CURRENT ARCHITECTURE

### What Exists ✓
1. **Core Blocks**: 22 core blocks styled/configured
2. **Theme.json Generation**: Automated via TypeScript
3. **Build Pipeline**: Webpack via wp-scripts
4. **SCSS Architecture**: ITCSS-based organization
5. **CSS Processing**: PostCSS with plugins
6. **Block Registration**: Vendor-based BlockManifest system
7. **Asset Enqueuing**: Custom Script/Style classes
8. **Development Tools**: make:block generators

### What's Missing ✗
1. **block.json Files**: No individual block.json metadata files
2. **Custom Blocks**: No custom block implementations (only core blocks)
3. **Block CSS Separation**: Block styles only in 5-blocks/ folder, not per-block
4. **Functional Block Code**: No Edit/Save components
5. **Block Render Templates**: No PHP render callbacks
6. **Manifest File**: blocks-manifest.php likely empty

### Key Architectural Decisions
- **Theme-First Approach**: Uses theme.json for all block customization
- **Centralized Theme Config**: Single source of truth in TypeScript
- **ITCSS Structure**: Layers CSS from generic to specific
- **Type-Safe Theme.json**: Full TypeScript support via generated types
- **Simplified Block Flow**: Minimal per-block file structure
- **PostCSS Enhancement**: CSS features via plugins, not SCSS alone

## IMPORTANT FINDINGS FOR IMPLEMENTATION

1. **Build System**: Uses @wordpress/scripts, NOT webpack directly
   - Custom filtering via bin/wp-scripts-filter.js
   - Needs --blocks-manifest and --experimental-modules flags

2. **Block Metadata**: Currently NO block.json files
   - Would need to be created in build output or source
   - Or use block.json generator from @wordpress/scripts

3. **PHP Registration**: Uses custom BlockManifest class
   - Expects manifest file at: build/blocks/blocks-manifest.php
   - Registers blocks via: wp_register_block_types_from_metadata_collection()

4. **CSS Handling**: Centralized in src/css/, not per-block
   - Block styles use WordPress CSS class names
   - SCSS @use syntax throughout

5. **Development Workflow**: Three parallel processes
   - wp-scripts for blocks
   - wp-scripts for assets
   - Node script for theme.json generation
